The checkpoint behind the M5 result. Format follows the dataset card ([03](03-dataset-card.md)).

## Training data

1,240 trajectories, 40 per kind-variant, from the training split only (`data/train.jsonl`), built
by `train/build_sft.py --n 1240 --policy runbook` (sha `bbc7172cbe1c…`, 2.12 M tokens, 4,080
assistant turns). Each trajectory is the observation-only runbook policy (`baselines/runbook.py`)
run through the real executor, rendered with the base model's own chat template. Loss is on
assistant turns only. No held-out task, template, entity or scenario is in it (M2 audit), and no
first call gives the answer away (`tests/test_sft_policy.py`). Everything is synthetic: generated by
the deterministic task generator, with no human data and no teacher model.

## Training procedure

One epoch, 155 optimizer steps of 8 examples (batch 1, gradient accumulation 8), AdamW lr 2e-4 with
5 warm-up steps and cosine decay, gradient checkpointing, bf16 base weights, seed 0. 6 h 41 min on
a shared GB10, peak 19.8 GiB allocated. torch 2.7.0a0 (NVIDIA build), transformers 5.14.1, peft
0.21.2 (`train/ENVIRONMENT.md`).

## Evaluation

Accuracy by resulting sandbox state, temperature 0, the base system prompt, the same tool set,
12-step and 3-retry budget as every baseline ([05](05-evaluation.md)).

| Set | Success | 95% CI |
| --- | --- | --- |
| test_unseen (primary: held-out templates, entities and scenarios) | 130/155 (84%) | 0.77–0.89 |
| test_template | 137/155 (88%) | 0.82–0.93 |
| test_entity | 134/155 (86%) | 0.80–0.91 |
| test_scenario | 130/155 (84%) | 0.77–0.89 |
| test_seen | 140/155 (90%) | 0.85–0.94 |

On test_unseen it beats Qwen2.5-14B-Instruct with the improved prompt (73%; 10 vs 27 discordant
tasks, p = 0.0076). On project 01's 60 held-out general prompts it scores 59/60, the same as the base
model, and never answers a plain prompt with a tool call.

## Intended use and limits

- **For the study only.** It demonstrates that a small model tuned on procedure traces can beat a
  larger prompted model on this task. It is not an operations agent to deploy.
- **Tied to its tool interface.** In project 02's own live harness, which has different tools
  (separate metric tools, a runbook tool, `submit_diagnosis`) and prompt for the same services, it
  scored 12/30 against the base model's 16/30 (p = 0.42; `results/summary/m5-transfer.md`). Use it
  only with the interface it was trained on.
- **Known failure points** (val): telling a bad config from a bad deploy, escalating when the bad
  change is not the latest version, reading queue growth, and threshold comparisons on heartbeat
  age (`results/summary/m5-analysis.md`).
- **One training seed so far.** Latency and memory, measured alone on an idle GPU: model call
  p50 0.55 s, episode p50 3.3 s, 6.3 GB of GPU memory at Q4_K_M (`results/summary/latency.md`).
- **It still acts wrongly sometimes:** 22 unallowed effects over 155 test_unseen episodes (the 14B
  with the improved prompt: 24). Anything real would need 02's approval layer in front of it.

## Reproduce

```bash
train/.venv/bin/python -m train.build_sft --n 1240 --policy runbook --out .run/sft/runbook-1240.jsonl
train/.venv/bin/python -m train.sft --data .run/sft/runbook-1240.jsonl --out .run/adapters/runbook-1240 --epochs 1
train/.venv/bin/python -m train.export .run/adapters/runbook-1240
env/models.sh serve models/qwen2.5-7b-lora-runbook-1240-Q4_K_M.gguf 21004 lora-runbook-1240-7b
.venv/bin/python -m eval.run_model --url http://127.0.0.1:21004 --condition lora-runbook-1240-7b --sets test_unseen
```

Serving with 4 parallel slots is not bit-deterministic; a rerun can differ by a few tasks
([04](04-fine-tuning.md) § Export and the reload check).
